# Stage 1 — The config builder

**Mockups:** `1a` (new config, search open) · `1b` (seven settings, live validation, YAML panel)
· `1c` (all 16 value shapes) · `1d` (flat chaining)
**Status:** functional baseline built; UI/completeness pass active
**Depends on:** nothing
**Blocks:** Stage 2 (Edit/New beside the config picker), Stage 4 (docking), Stage 6 (chain map)

## Problem

Nothing in the app can produce a Workbench YAML. The user writes it in an editor, guesses at
key names out of ~142 possible settings, and finds out what is wrong only when
`workbench --check` fails. This stage makes the app the place configs are written.

## Decisions taken (by the user, 2026-08-30)

- **Catalogue source:** checked-in JSON generated by a script from `WorkbenchConfig.py`, plus a
  GitHub workflow to refresh it manually or by webhook.
- **Editors:** all 16 value shapes from mockup `1c` in this stage, not a subset.
- **Validation:** local checks only. No network lookups (vocabulary lists, term URI resolution)
  in this stage.

## 1.1 Setting catalogue, generated from Workbench

`WorkbenchConfig.get_default_config()` (`WorkbenchConfig.py:430` in the workbench checkout) is a
flat Python dict literal of ~140 keys with real defaults. It carries **no** descriptions, enum
choices or shape hints — those come from a hand-maintained override file.

### `scripts/gen-config-catalog.py` (new)

- Parse `WorkbenchConfig.py` with `ast` — never `exec`; the file imports the world.
- Locate `get_default_config`, read the returned dict literal.
- Infer a default shape from each literal:
  `bool` → `boolean` · `int` → `integer` · `str` → `string` · `list[str]` → `list_of_strings` ·
  `list[int]` → `list_of_numbers` · `list[dict]` → `list_of_one_key_maps` · `dict` → `map` ·
  `None` → `nullable_enum` candidate.
- Deep-merge `crates/workbench-integration/catalog_overrides.json` (hand-written, checked in)
  over the inferred entries. Override keys: `description`, `shape`, `choices`, `required`,
  `group`, `unit`, `tokens` (for `template_string`), `browse` (`file` | `dir`).
- Emit `crates/workbench-integration/config_catalog.json`:

  ```json
  { "workbench_ref": "<git sha>", "generated": "<iso date>",
    "settings": [ { "key": "...", "shape": "...", "default": null, "description": "...",
                    "choices": [], "required": false, "group": "..." } ] }
  ```

- Exit non-zero if a key present in the overrides is absent upstream. That is the drift signal.

Descriptions are the expensive part and are written by hand into the overrides file. Ship with
the ~30 settings the mockups and `test.config.yml` actually use described, and an empty string
for the rest; fill in by demand.

### `.github/workflows/config-catalog.yml` (new)

- Triggers: `workflow_dispatch` (input `workbench_ref`, default `main`) and
  `repository_dispatch` (type `workbench-updated`) so an upstream webhook can drive it.
- Steps: checkout this repo → checkout `islandora/islandora_workbench` at `workbench_ref` into a
  temp path → `python scripts/gen-config-catalog.py --workbench <path>` → if
  `config_catalog.json` changed, open a PR titled `chore: refresh config catalog (<ref>)`.
- **Does not auto-tag a release.** Merging the PR onto `main` feeds the existing release
  pipeline (`docs/SETUP.md`); firing the release stays a human `workflow_dispatch`.

### `crates/workbench-integration/src/config/catalog.rs` (new)

```rust
pub enum Shape {                       // all 16 from mockup 1c
    Boolean, Integer, String, Delimiter, Enum, NullableEnum, FilePath, Url,
    ListOfStrings, ListOfNumbers, ListOfOneKeyMaps, Map, MapOfLists,
    CommandList, TemplateString, ConfigRef,
}
pub struct SettingDef { key, shape, default: serde_yaml::Value, description,
                        choices, required, group, unit, tokens, browse }
pub fn catalog() -> &'static [SettingDef];   // LazyLock over include_str!("../config_catalog.json")
```

`TASK_OPTIONS` (`crates/app/src/app_settings/custom_fields.rs`) becomes the `choices` of the
`task` entry in `catalog_overrides.json`. Keep the Rust const as a thin re-export off the
catalogue so the existing settings pages keep compiling unchanged.

## 1.2 Draft model + YAML I/O

Add `crates/workbench-integration/src/config/draft.rs`. **Do not disturb** the `Pending` /
`Ready` type-state in `config/runtime.rs` — `run_ingest` and `update_config_fields` depend on it.

```rust
pub struct ConfigDraft {
    pub path: Option<PathBuf>,
    pub label: String,
    pub values: IndexMap<String, serde_yaml::Value>,
}
impl ConfigDraft {
    pub fn load(path: &Path) -> anyhow::Result<Self>;
    pub fn to_yaml(&self) -> String;
    pub fn save(&self, path: &Path) -> anyhow::Result<()>;
}
```

`IndexMap` keeps key order stable so the YAML preview does not reshuffle between renders.
`host`, `credentials_file_path` and `input_csv` are **never** in `values` — the app writes them
at run time. The builder shows them as the locked band from mockup `1a`.

## 1.3 Local validation — `crates/workbench-integration/src/config/validate.rs` (new)

```rust
pub enum Severity { Error, Warn, Ok }
pub struct Problem { pub key: Option<String>, pub severity: Severity, pub message: String }
pub fn validate(draft: &ConfigDraft) -> Vec<Problem>;
```

Rules, all local:

- shape conformance, and `required` (only `task`);
- path settings — does the parent folder exist, is it writable (mockup `1b`'s check line);
- a hand-written cross-field table, seeded from the mockup's own examples:
  - `timestamp_rollback: true` with empty `rollback_dir` → **Error** (without it the run cannot
    be undone),
  - `allow_missing_files: true` → **Warn**,
  - a large `adaptive_pause` → **Warn** with the row-count estimate.

Keep the cross-field table a plain slice of closures. It grows one rule at a time.

## Notes discovered during implementation

_(a future agent should read this section first — it records where reality differed from the
plan above)_

**`get_default_config()` holds 125 keys, not ~142.** The canvas's number counts settings
Workbench *recognises* but has no default for, so they never appear in that function —
`task`, `host`, `credentials_file_path`, `shutdown`, `bootstrap`, `adaptive_pause`,
`csv_field_templates`, the `rollback_*_template` pair, and about thirty more. The overrides
file therefore has **two** sections: `settings` patches keys that have an upstream default,
and `extra` adds complete entries for keys that do not. The generator errors if an `extra` key
later gains an upstream default, so the two can never silently duplicate. The catalogue
currently ships **167** settings; `extra` is curated and grows by demand.

**Eleven defaults are not literals.** Five are `@staticmethod`s on the same class that return a
literal (`self.get_media_types()`, `get_media_fields()`, …) — the generator follows those, plus
`dict()` / `list()` / `dict({…})` written the long way. Three are internal, not user settings
(`check`, `get_csv_template`, `path_to_workbench_script`) and are `skip`ped. The rest
(`tempfile.gettempdir()`, `os.path.join(…)`) take a `default` from the overrides.

**A `group` fall-back lives in the generator**, not the overrides. Assigning a section by hand
to 125 keys was 125 lines of boilerplate to say `log_*` is logging; `infer_group()` does it by
key name and an override still wins.

**`helpers::get_file` is now generic over the view** (`Context<T>` rather than
`Context<Workspace>`) so the builder can use the same browse dialog. One-line change, no
behaviour difference for the workspace.

**Widget state is keyed, not structured.** `field_id(&["csv_value_templates", "0", "k"])`
produces `csv_value_templates#0#k`; `read_widgets` reads the same ids back. Setting keys are
`[a-z0-9_]` upstream so `#` cannot collide. Adding or removing a row calls `forget_widgets`,
dropping that setting's inputs so the survivors are rebuilt from the draft rather than left
holding values that have shifted up a row. **The draft is the single source of truth** — do not
add a second editable representation.

**All six list/map shapes share one renderer** (`render_rows`), fed by `rows_of()`, which
normalises them to `(left, Vec<right>)` pairs. Adding a container shape means an arm in
`rows_of`, `read_widgets` and `render_rows` — not a new editor.

**The original gpui-component 0.5.1 icon limitation is no longer the dependency baseline.** The
workspace now follows the same upstream git components as qrate. The Settings row still uses
`Settings2`; revisit it against the current icon catalogue when that row is next redesigned.

**A new builder window is re-keyed after its first successful save.** The open-window registry
removes its `None` entry and inserts the saved path with the same window handle. “New config” can
therefore open a fresh draft, while Edit focuses the one live draft for that file. Linked-config
existence checks are cached and refreshed at most every two seconds instead of calling `is_file`
for every link on every frame.

**Not built, deliberately:** keyboard navigation in the search palette (`↑↓`/Enter/Esc from
mockup `1a` — it is click-and-Add today), drag-to-reorder in the chain list, and the
`csv_value_templates` column/template header row. None blocks the flow; add them when the
palette is actually used at speed.

**Follow-up reopened on 31 August 2026.** The functional baseline is not the final builder UI.
The separate Add setting toggle, tall runtime-supplied card, non-selectable YAML labels, fixed
window height, inconsistent control density, and pointer-only palette are tracked in
[the UI quality pass](ui-quality-pass.md). Recursive chaining moved forward from Stage 6 into the
same pre-docking pass because it changes the builder's structure and child-window plumbing.

## Phase 1 — a builder-authored config must run (October 2026)

The audit in `tmp/IMPLEMENTATION-PLAN.md` (§3.1, P0-1…P0-11) found that a config made in the
builder could not be checked or run. Tasks 1.1–1.10 of that plan fix it, one commit each, each
with a unit test. Exit gate: build a config from scratch, link a child, pick a server, press
**Check**, and Workbench parses it.

- [x] **1.1 (P0-1)** `WorkbenchConfigFile` no longer requires `host`, `credentials_file_path` or
  `input_csv`; all three are `Option` and are not written back when absent, nor is
  `secondary_tasks: null`. A builder config (`task: create` and nothing app-supplied) loads and
  gains host and credentials from `update_config_fields`.
- [x] **1.2 (P0-2, Q2 default)** The app now supplies `input_csv`. `Workspace.processed_csv` holds
  the path the processor *reported* (a script may write somewhere other than
  `input_data/metadata.csv`); it is cleared when the source or processor changes. At Check/Run
  `update_config_fields(&RunOverrides { host, credentials_file_path, input_csv }, workbench_dir)`
  writes it into the **root** config only — secondary configs keep their own CSV. With no
  processed CSV the file's own `input_csv` stands; with neither, Check/Run refuses before
  writing anything ("No input CSV: process a source in step 1, or set input_csv in …").
  "Open processed" reveals the stored path. Note: upstream Workbench defaults `input_csv` to
  `metadata.csv` inside `input_dir` (`input_data`), which happens to be where the built-in
  processor writes — so the old behaviour often worked by coincidence, and stops working as
  soon as a script or a custom `input_dir` is involved.
- [x] **1.3 (P0-3, Q3/Q8 defaults)** The run-time update no longer re-serializes the user's file.
  `config::patch::set_top_level_scalars` replaces (or appends) only the `host`,
  `credentials_file_path` and `input_csv` lines; every other byte — comments, quoting, order,
  CRLF — is untouched, and an unchanged file is not rewritten at all. The result is re-parsed
  and must equal "original plus exactly these keys"; a document the patcher declines (flow
  mapping, several documents) or misreads falls back to re-serializing, with a log warning.
  Patched values are quoted for **YAML 1.1** as well as 1.2: Workbench reads configs with
  PyYAML, where a bare `yes`, `on` or `1:20` is not a string. Q3 stays "keep editing in place";
  running from a generated copy is still the long-term option. For the builder (Q8), the
  minimum option: `ConfigDraft.source_has_comments` records that a loaded file has comments so
  the builder can ask before its first save drops them (the prompt lands with the confirm
  dialog in 1.7).
- [x] **1.4 (P0-4)** One rule for `secondary_tasks` paths, verified against upstream Workbench:
  it turns each entry into `os.path.abspath(entry)` in the primary process, and the app starts
  that process in the Workbench directory, so a relative entry (at any depth) is relative to
  **the Workbench directory**, not to the config naming it. `config::resolve_secondary_task` is
  the one resolver; the run-time rewrite, `chain::{child_nodes, flattened_paths, link_error}`
  and the builder all take the Workbench dir as a parameter (the builder reads
  `workbench_path` from Settings; with none set, the config's folder is a display-only
  fallback). Both link flows — "Create a new one" after first save, and "Link an existing
  config" — now go through `ConfigDraft::link_secondary_task` and write **absolute** paths.
  Also found: Workbench does not add `.yml` to an entry, so the chain's lenient
  `create-items.config` → `create-items.config.yml` discovery now marks the node broken with
  "relink it as create-items.config.yml" instead of treating it as healthy; and the run-time
  rewrite recursed without a visited set, so a hand-written loop overflowed the stack — it now
  stops with an error.
- [x] **1.5 (P0-5)** "Unset" exists: `Value::Null` in the draft means the row is present but
  the key is not written (`ConfigDraft::to_yaml` filters nulls), so Workbench applies its own
  default. An integer field that is empty or a lone `-` reads back as unset
  (`editors::parse_integer`, never a string); a new integer row with no upstream default starts
  unset rather than `0`; the field's placeholder shows the default. Validation accepts null for
  every non-required setting. This also makes a nullable enum's `none` really omit the key, as
  its row always claimed.
- [x] **1.6 (P0-6)** Templates are reachable. They showed only when the draft had no values,
  but every draft starts with `task`; they now show while `ConfigDraft::is_blank()` — no setting
  except an unset `task`. `apply_template` already worked from that state.
- [x] **1.7 (P0-7)** `ui::confirm_dialog` is the spec's ConfirmDialog (§09): a thin layer over
  gpui-component's `AlertDialog` — 420 px (`tokens::CONFIRM_DIALOG_W`), title as a question,
  body saying what is kept, ghost Cancel, danger action with a verb. The builder now renders
  `Root::render_dialog_layer`, which it never did, so no dialog could show in it. "Discard
  draft" asks first and then re-reads a saved config from disk, or resets a never-saved one to
  its required settings (the old Discard emptied the form, `task` included); it is enabled only
  while the draft may differ from the file. Q8's warning lands here too: the first save over a
  loaded file that has comments asks "Save over <name>?" before dropping them.
- [x] **1.8 (P0-8)** A new config's file name is `slug(label)`: lowercase `[a-z0-9_-]`, anything
  else collapsed to `_`, empty → `new_config`, so `../../x` or `a:b` cannot escape or break the
  library folder. An existing file is never overwritten by a draft that did not load it: the
  name gets `-2`, `-3`, …. The plan's "Save as…" path prompt is not built — the suffix already
  removes the overwrite, and a prompt is one more modal on the most common action.
- [x] **1.9 (P0-9)** Chain edits have one path, `ConfigBuilder::apply_chain_edit(owner, edit)`:
  this window's draft when `owner` is the config open here; else the draft of another open
  builder window on `owner` (which is marked edited, so its next Save keeps the change); else
  the file. `ConfigBuilderWindows` now records each window's view (`OpenBuilder { window,
  view }`), matched by file identity. Unlink and "link after first save" both use it, through
  `ConfigDraft::{link,unlink}_secondary_task`. This also fixed a case the audit missed:
  unlinking a **top-level** node of a saved root edited the root's file on disk behind its own
  open draft, so the next Save put the link back. Only the file fall-back has a unit test; the
  window routing needs a GPUI test context (plan 9.2).
- [x] **1.10 (P0-10/11)** `validate` takes a `ValidationContext { workbench_dir }`, and the
  self-link rule resolves each entry the way Workbench does and compares file identity
  (`chain::same_path`) — two `main.yml`s in different folders are no longer an error. The plan
  suggested `chain::link_error`; that also reports "already in the chain" for every existing
  entry, so only its identity check is reused. App-supplied keys found in a loaded file are no
  longer a footer warning with no row to click: the locked band says "set in file — replaced
  by the ingest server" (or, for `input_csv`, "used unless step 1 processes a source").
