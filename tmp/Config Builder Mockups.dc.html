READ MEHow this canvas is organised, and what it assumes
Layout

One group per subject, stacked top to bottom; the mockups inside a group read left to right. Groups are ordered by how far out they sit from the config builder: settings and profiles first, then the main window, then window placement, then chaining, then the builder itself and its input vocabulary.

Every mockup keeps a permanent id — 3b, 2a, 1c — so you can point at one in chat and I will know exactly which.

Grounding

Chrome, spacing and controls follow the GPUI app: 40px title bar, bottom status bar, small-radius inputs, and for the settings window the real page / group / item structure from app_settings/mod.rs.

Every option name, type and default is real, read from WorkbenchConfig.py (~140 keys) and your test.config.yml. Task names come from TASK_OPTIONS.

Standing assumptions

task is the only setting the builder demands. host, credentials_file_path and input_csv are written by the app at run time and shown as a locked band so nobody thinks they are missing.

Two accent families appear: groups D–F use the SACDA orange from the first pass, groups A–C use the design system's amber app-chrome tokens. Same intent, marginally different hue — say the word and I will settle on one.

What's here now

Three pages — Paths, Servers, Task Configs — each a list of groups, each group a list of label / description / control rows. Saved servers and saved configs are read-only rows with a remove button.

Where it strains

  • A saved config is only a label, a task name and a path to a YAML someone wrote elsewhere. Nothing in the app can produce that file.
  • Adding an entry is a separate group from the list of entries, so the page reads as two unrelated forms.
  • Entries can be removed but not edited or renamed — a typo in a URL means delete and retype.
  • Everything is global to the machine. There is one server list and one config list, so a dev credential and a production host can be paired by accident.
  • Nothing here can be handed to another institution; setup lives in a document instead of a file.

Kept in the rework

The page / group / row anatomy is good and matches the rest of the app. 3b keeps it and changes what sits inside.

The problem

Today every setting is global to the machine: one server list, one config list, one input step. That is exactly right for one person ingesting for one institution, and it breaks in three ordinary situations.

Three situations

  • Dev and production side by side. Same config library, different hosts and credentials. Nothing currently stops a config written for dev being run against production.
  • Another institution. They need their own servers, sources and configs, and none of ours. Without profiles the app has to be re-set-up by hand and ours has to be deleted.
  • A second machine. Onboarding today means following a setup document. With profiles it means opening a file.

Why a bundle, not more settings

The dangerous mistakes are mismatches — a dev credential with a production host, our transform script against someone else's sheet. Grouping the institutional settings into one named thing that switches atomically removes that class of mistake, which a longer settings list does not.

The cost, and how it's paid

Profiles are one more concept for someone who only ever needs one. So the app ships with a single profile called Default, the Profiles page is the last item in the sidebar, and the switcher in the main window stays hidden until a second profile exists. Nobody meets the idea until they need it.

Open question

Does the config library belong to the profile or to the machine? Institutional, as drawn here. But if you keep one folder of YAML shared across profiles, it should move out — worth deciding before this is built.

What changed

Step 1 was the only institution-specific part of the window. It now has three fields and no site knowledge: the input source picks where rows come from, its Sheet URL and Ingest dir are always shown, and a single preprocess script dropdown replaces the hard-coded SACDA transform. The collection node ID is gone — it belongs in the script, not in the window. A site with no transform picks None and just presses Process.

Profiles

Everything site-specific — input source and its values, server list, credentials, config library — lives in a named profile. SACDA keeps "SACDA — UFV"; another institution creates its own and never sees ours. This also gives a clean export: hand someone a profile file instead of a setup document.

Three numbered steps

Input source, config, server — in the order a run actually happens, with step 1 marked optional because a site that already has its CSV skips it. The config row grew a chain count and Edit / New, so the builder is reachable from the place the config is chosen.

Open question

Preprocess scripts are listed from a folder set in Settings — see 3b. Open question: do they need to declare anything (a name, expected columns) or is a bare .py file that writes metadata.csv the whole contract?
